🏠화면 개요

예약상세 화면은 기본탭 / 원장탭 두 개로 구성. 한 예약에 대한 모든 운영 작업을 한 화면에서 처리해요.

🔥 자주 쓰는 케이스 Top 5

신규 예약시스템에서 새로 해결된 6가지 핵심 문제 — 운영자가 가장 자주 마주칠 케이스

  1. 한 예약에 결제주체 여러 개 (여행사 + 채널 + 트립 결제 조합)
    예약을 두 건으로 쪼개지 않고도 정산 처리 가능. 여행사 결제는 관리자 수정 O / 채널사 결제는 자동생성 후 수정 X (PG 연동 보호)
    → ⑧ 원장탭에서 결제주체별 잔액·이력 확인. ⑦ 결제 정보에서 분할된 결제 행 확인
  2. 결제링크 한꺼번에 못 보내는 거 (카드 한도·여행자별 분할 결제)
    기존 = 새 링크 만들면 기존 자동 만료 → 신규 = N개 동시 유효. 수신자별 휴대폰·금액 직접 입력
    → ⑦ 결제 정보 ▷ 결제 URL 전송 ▷ 다중 수신자 + [1/N 균등분할]
  3. 결제수단 변경할 때 예약금액 수정해야 하는 거
    기존 = 100→200→100 수동 조작 → 신규 = 예약금액 그대로 두고 재결제 링크만 발송. 사용자 "내 예약" 금액 일관 유지
    → ⑦ 결제 정보 ▷ 결제수단 변경 ▷ 4단계 프로세스
  4. 인원 추가/취소 시 할인금액 수기 계산 (자동 처리)
    기존 = 쿠폰·특가 운영자가 직접 계산해서 추가할인에 입력 → 신규 = 인원 변동 시 판매가 비율로 쿠폰 자동 차감 + 100·202 자동 역분개. 인원 삭제 후 [+금액 추가] 자동 표시 (위약금 입력용)
    → ④ 인원 관리 ▷ 인원 삭제 → 자동 ⑤ [+금액 추가] 모달
  5. 취소위약금 결제금액에서 따로 매겨야 하는 거 없애기
    기존 = 결제시스템에서 따로 관리 (이중 작업) → 신규 = 예약 원장 701로 통합. 결제 영역은 "결제·환불"만 관리
    → ⑤ 예약 금액 관리 ▷ +금액 추가 ▷ 취소위약금(701)
💡 +1 정책 정리 필요 케이스: 취소된 예약정보의 금액을 어떤 기준으로 볼지 (취소완료 시 화면별 표시 정책) → ⑪ 정책 매트릭스 참고

예: 여행사가 자기네 행사 코드를 바꾸고 싶을 때. 손익 정보·소싱·인벤토리에 영향 없음.

예: 100만 원짜리 → 110만 원짜리 변경 시 +10만 원 자동, 8만 원만 받기로 합의면 -2만 원 별도 할인 입력.
💡 설계 핵심 (전무님 결정):
• 행사 정보 변경과 행사 이동(가격 변경)을 분리하여 액션마다 책임 명확화
• 우리 시스템의 행사코드(travelId)는 임의로 조작하지 않음 → 안정성 확보
• 여행사 관리용 코드는 별도 필드 → 여행사 자유 수정, 우리 인벤토리에 영향 X
