🎯 이 테이블이 하는 일

"이 예약이 누구의 것이고, 어떤 채널·여행사에 속하는지" 정체성을 담음. 한 예약 = 한 행이며, 모든 금액·여행자·행사는 이 원장 1행을 중심으로 매달림.

왜 이렇게?

  • 예약 = 1행이라는 정체성을 잃지 않기 위해. 결제주체가 둘이어도 원장은 하나.
  • 예약자 정보(booker_*)는 스냅샷으로 보존 — 회원 정보 변경에 흔들리지 않음.
  • channel · agency는 식별자만. 결제·정산 분기는 ledger_items가 담당.

🎯 이 테이블이 하는 일

예약이 어떤 행사(travel)에 연결돼있는지 매핑. 행사 이동 시 기존 행 valid=false로 두고 새 행 추가 → 이력 자동 보존.

왜 분리됐나?

  • 현행은 ts_reservation에 travel_id가 1컬럼 압축돼있어 행사이동 이력이 사라짐.
  • 신규는 별도 테이블 + valid 토글 → 이력 테이블 따로 안 만들어도 됨.
  • 마감 행사 이동·다중 행사 매핑(2차) 대응 여지 확보.

💡 현행 데이터는 행사이동 이력이 컬럼 덮어쓰기로 사라짐 → 마이그 시 현재 상태 1행만 valid=true로 생성.
행사이동 정책 결정

🎯 이 테이블이 하는 일 — 시스템의 심장

예약에서 일어나는 모든 금액 거래 1건 = 1행. 상품가·할인·쿠폰·결제·환불·정산·위약금 전부 여기에 들어옴. 덮어쓰기 절대 없음 → 모든 이력 보존.

왜 다중 행?

  • 분할결제·인원별 금액·역분개·정산을 자연스럽게 표현.
  • 정책 변경(쿠폰 자동·위약금 1/n)이 행 추가/룰만으로 흡수.
  • 주체별 잔액 = 코드 범위별 +/− 합산으로 즉시 계산.

🎯 이 테이블이 하는 일

39개 원장 항목 코드의 정체(이름·범주·부호·범위)를 enum 형태로 관리. 하드코딩 방지 + 신규 항목 추가가 마이그레이션 없이 가능.

  • 신규 항목 추가가 잦음 (정책 변경에 따라). 코드 배포 없이 데이터로 추가.

③ 주요 시나리오 — Legacy vs 신규 비교

📍 1. 신규 예약 (3명 패키지, 트립직판)

rsv_ledgers ×1rsv_travels ×1 rsv_channel_links ×1rsv_agency_links ×1 rsv_travelers ×3rsv_ledger_items ×7
Legacy (ts_*) ts_reservation ×1 + ts_reservation_order ×1 (금액 컬럼 압축) + ts_reservation_travelers ×3 + ts_agency_reservation_detail ×1. 인원별 금액 안 보임.
신규 (rsv_*) 원장 1 → 행사 1 → 채널/여행사 링크 각 1 → 여행자 3 → 원장 항목 7행(상품가 ×3, 특가 ×3, 쿠폰 ×1). 인원별 금액 명시.

📍 2. 분할 결제 (1차 9번)

rsv_ledger_items (type=401) +2행
Legacy (ts_*) ts_reservation_order.payment_amount 컬럼 덮어쓰기 + 별도 PG 결제 테이블 JOIN. 이력 추적 어려움.
신규 (rsv_*) 원장은 그대로. ledger_items에 type=401 결제 행 2개 추가. 예약 쪼갤 필요 X. ref_payment_id로 PG 트랜잭션 매핑.

📍 3. 행사 이동 (1차 2번 — 정량효용 1등)

rsv_travels +1행 (기존 valid=false) rsv_agency_links (옵션) rsv_ledger_items (100/202/301/302)
Legacy (ts_*) ts_reservation.travel_id 덮어쓰기. 이전 행사 정보 사라짐. 금액 차액·쿠폰 재계산은 컬럼 덮어쓰기.
신규 (rsv_*) travels 새 행 추가 + 기존 valid=false. 금액 차액·특가·쿠폰 재계산은 ledger_items 자동 행 추가. 이력 완전 보존.

📍 4. 인원 1명 취소 + 위약금 (1차 4번)

rsv_travelers status=CANCELED rsv_ledger_items 역분개 +N행 rsv_ledger_items type=800
Legacy (ts_*) ts_reservation_travelers 컬럼 변경 + ts_reservation_order 금액 컬럼 덮어쓰기. 위약금은 결제시스템에서 따로 처리.
신규 (rsv_*) 여행자 status 변경 + 해당 인원의 100/202/… 역분개 행 추가 + 위약금 행(800). 위약금이 예약시스템으로 이동.

📍 5. 부분 환불

rsv_ledger_items (type=703 +1행)
Legacy (ts_*) 별도 환불 테이블 + payment_amount 차감. 원본 결제와 환불의 연결 추적 어려움.
신규 (rsv_*) type=703 행 추가. 기존 결제 행(401) 그대로. ref_payment_id로 원본 PG 트랜잭션 연결.

📍 6. 결제주체 둘 (채널 + 플랫폼) — 신규에서만 가능

rsv_ledgers ×1 (한 원장) rsv_ledger_items (type=400+401)
Legacy (ts_*) 구조 표현 불가 → ts_reservation을 2개로 쪼개서 운영. 두 예약의 정합·정산 수동 처리.
신규 (rsv_*) 한 원장 안에 type=400(채널결제) + type=401(플랫폼결제) 행 공존. 도메인적으로 자연스러움.
