① 최종 결정

3가지 결정 사항을 한 번에 정리합니다.

결정 1 · 옵션 B 채택
기존 [예약완료] 상태값을 "출발대기"의 의미로 재해석합니다. 별도 [출발대기] 상태값을 추가하지 않습니다.
결정 2 · 2-Flag AND 룰
예약접수 → 예약완료 전환은 ① 여행사 확정 OK + ② 결제완료 두 조건 모두 충족 시 시스템이 자동 처리합니다.
결정 3 · A안 (책임 분리)
여행사가 [예약완료 처리] 버튼을 누르면 버튼은 즉시 활성되고 sub-status로 "여행사 확정, 결제 대기"가 표시됩니다. 결제완료가 들어오면 시스템이 자동으로 예약완료 전환.

⑤ 책임 분리 — 사람 vs 시스템

A안 채택으로 책임 영역이 명확해집니다.

🧑‍💼 여행사 (사람 액션)

  • 고객 확인 (출발 의사)
  • 상품 출발 가능 여부 확인
  • [예약완료 처리] 버튼 클릭 = Flag ① ON
  • 이후엔 결제 추적/안내만 (Flag ②는 시스템 책임)
✓ 책임 종료 마커: 버튼을 누르면 여행사 책임은 끝. 결제 미입금이라도 sub-status에 "결제 대기" 표시되어 알 수 있음.

🤖 시스템 (자동 처리)

  • 결제 라운드 완료 감지 = Flag ② ON
  • 2-Flag AND 충족 시 자동 전환 (예약접수→예약완료)
  • 출발일 도래 시 자동 (예약완료→출발완료)
  • 정산 데이터 자동 생성 (출발완료 기준)
✓ 자동 처리 영역: 운영자가 손댈 일 없음. Flag만 충족되면 다음 상태로 자동 진행.

⑥ 왜 A안인가

[예약완료 처리] 버튼이 결제 미입금일 때 어떻게 동작할지 — A안과 B안 비교.

✅ A안 (채택)
버튼 활성 + sub-status로 표시
  • ✓ 여행사가 버튼 누름 → Flag ① 즉시 ON
  • ✓ 결제 미입금이어도 액션 종료 (자기 책임 끝)
  • ✓ 화면에 "여행사 확정 ✅ · 결제 대기" 표시
  • ✓ 결제완료 들어오면 자동으로 예약완료 전환
  • ✓ 책임 분리 명확
❌ B안 (기각)
버튼 비활성 ("결제완료 후")
  • ✕ 결제 미입금이면 버튼 누를 수 없음
  • ✕ 여행사가 자기 책임 다 했어도 액션 차단
  • ✕ 결제 추적 책임이 여행사로 떠넘겨짐
  • ✕ "왜 안 눌리지?" 혼란
  • ✕ 책임 경계 모호

⑦ 이 결정으로 얻는 효과

단순한 상태값 정리 이상의 부가 가치.

1. 운영자 멘탈모델 단순 "예약완료 = 모든 게 OK 출발 준비 끝" / "예약접수 = 뭔가 더 필요"의 단순한 2분법으로 직관적
2. 상태값 추가 없음 기존 [예약완료] 의미만 재해석. 시스템/DB 변경 최소화, legacy 호환
3. 책임 분리 명확 여행사 = 버튼 클릭으로 책임 종료 / 시스템 = 결제완료 감지 + 자동 전환
4. KPI 측정 가능 Flag ① 평균 처리 시간 = 여행사 응답성 / Flag ② 결제 완료 소요 = 결제 흐름 효율성
5. 고객 안내 분리 "여행사 확정 대기" vs "잔금 결제 대기" — 어느 단계에서 멈춰있는지 정확히 안내 가능
6. 화면 단순화 탭을 6개로 쪼개지 않아도 됨 → sub-status pill로 빠른 좁히기. 통합 테이블 가능
