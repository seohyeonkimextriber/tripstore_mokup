예약상태 정의 — 옵션 1 vs 옵션 2

"출발대기"를 어떻게 다룰지에 대한 두 가지 방안 비교. 영업실·개발팀과 합의 후 노션 정책 페이지로 이관 예정.

🎯 풀어야 할 질문
"출발대기"는 새 상태값으로 추가할까, 예약접수 단계의 sub-status로 흡수할까?
1
옵션 1
"출발대기" 신규 상태값 추가
기존 흐름에 "출발대기"를 별도 상태값으로 추가합니다. 예약완료는 여행사 확정만 떨어진 단계, 출발대기는 결제까지 완료된 단계로 분리.
예약접수신규 진입
▶여행사 확정
예약완료결제 대기
▶결제완료 자동
출발대기신규 ★
▶출발일
출발완료
상태정의
예약접수여행사 담당자의 확정 대기. 고객 확인 + 출발 가능 확인 필요
예약완료여행사 확정 완료. 단, 결제는 별도 추적 (잔금 미입금 가능)
출발대기 신규여행사 확정 + 결제완료 모두 충족. 출발 대기 🤖 자동
출발완료출발일 도래. 정산 단계로 🤖 자동
👍 장점
  • 각 상태 의미가 단계별로 정확히 분리됨
  • "예약완료 + 미입금" 케이스 명확히 표현
  • 결제 추적 단계 시각화 강함
  • 화면(스크린샷)에 탭 하나만 추가 — 익숙함
👎 단점
  • 상태값 1개 추가 → 시스템 복잡도↑
  • 운영자가 "예약완료 vs 출발대기" 차이 헷갈릴 수 있음
  • "예약완료"라는 단어가 실제 "완료"가 아님 (혼선)
  • 탭이 7개로 늘어남 (좁아짐)
2
옵션 2
예약접수 sub-status로 흡수
"출발대기"의 정의 자체가 "결제완료 + 갈 수 있는 상태"이므로, 예약완료 = 출발대기로 의미 통합. 진행 중 케이스는 예약접수 탭 안의 sub-status로 관리.
예약접수진행 중
▶2가지 모두 OK
예약완료= 출발대기
▶출발일
출발완료
📌 예약접수 탭 안의 2가지 관리 포인트 ① 접수 신청 확인 건 — 여행사 담당자가 고객/출발 확인 필요
② 결제 필요 건 — 잔금 결제 대기 (시스템이 자동 추적)
→ 두 가지 모두 OK가 되면 예약완료(=출발대기)로 자동 전환
상태정의
예약접수진행 중 (접수 확인 ❌ or 결제 ❌). sub-status로 세부 단계 표시
예약완료
(= 출발대기 의미)		접수 확인 ✅ + 결제완료 ✅ 모두 충족. 출발 대기 🤖 자동
출발완료출발일 도래. 정산 단계로 🤖 자동
👍 장점
  • 상태값 추가 없음 → 시스템 단순
  • "예약완료 = 진짜 완료" 직관적
  • 탭 6개 그대로 유지 (변화 비용 낮음)
  • 예약접수 탭 안에서 모든 진행 케이스 통합 관리
  • 운영자가 한 탭 안에서 일 처리 (집중도↑)
👎 단점
  • 예약접수 탭이 다양한 케이스 섞임 → 시각화 중요
  • sub-status 개념 도입 → 운영자 학습 필요
  • "여행사가 OK했는데 왜 예약완료 아니지?" 초기 혼선 가능

💡 결정 가이드

어느 쪽을 선택해도 정답입니다. 우선순위가 다를 뿐.

옵션 1을 선택하세요 — 만약
  • 여행사가 탭 변화 최소화를 원할 때
  • 상태별 KPI/통계를 단계별로 명확히 측정하고 싶을 때
  • "예약완료지만 미입금" 케이스를 독립 시각화하고 싶을 때
  • 탭이 7개여도 부담 없을 때
옵션 2를 선택하세요 — 만약
  • "예약완료"라는 단어가 진짜 완료 의미이길 원할 때
  • 시스템/DB 변경 최소화가 중요할 때
  • 여행사 운영자가 한 탭에서 모든 진행 케이스를 보길 원할 때
  • sub-status 개념 도입에 거부감 없을 때
