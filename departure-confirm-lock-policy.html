자동 출발확정 후, 취소 발생 시 어떻게 처리할 것인가?

예약 인원이 최소출발인원에 도달해 출발확정이 되었는데, 이후 취소가 발생해 다시 인원이 미달되는 케이스. 이 상황을 어떻게 처리하느냐가 핵심 정책 결정.

5가지 해결 옵션

각 옵션의 작동 룰, 장단점, 운영 시나리오 비교.

옵션 A

자동 양방향 토글

매번 인원 변동에 따라 출발확정 ↔ 예약완료 자동 전환
if booked >= threshold:
  status = 출발확정
elif booked < threshold:
  status = 예약완료 // 매번
👍 장점
  • 늘 정확한 상태값
  • 구현 단순
👎 단점
  • 고객 알림 폭탄
  • 운영 혼란
  • 신뢰 무너짐
옵션 B

자동 단방향 Lock

첫 충족 시 출발확정, 이후 변동 무시 (한 번 lock되면 계속 lock)
if booked >= threshold and !locked:
  status = 출발확정
  locked = True
if locked:
  pass // 변동 무시
👍 장점
  • 가장 안정적
  • 고객 신뢰 보장
  • 알림 1회만
👎 단점
  • 출발 못 갈 행사도 lock
  • 모객 미달 처리 어려움
  • 운영 유연성 ↓
옵션 C

운영자 100% 수동

시스템은 알림만, 운영자가 [출발확정] 버튼 클릭 시에만 처리
if booked >= threshold:
  notify("운영자 확인 필요")
on operator_click_confirm():
  status = 출발확정 // Lock
👍 장점
  • 가장 안전 (사람 판단)
  • 책임 명확
👎 단점
  • 자동화 효용 X
  • 69% 자동 매핑 효과 상실
  • 운영자 부담 ↑
옵션 D · 추천 ⭐

시한 기반 Lock

출발일 D-N(예: D-7) 전엔 양방향 자동 / D-N 이후엔 lock
if days_to_departure > 7:
  // 양방향 자동 OK
  status = if booked >= threshold else 예약완료
elif days_to_departure <= 7:
  // LOCK
  status = locked
👍 장점
  • 운영 현실 정합
  • D-7 이전 변동 자유
  • D-7 이후 안정 보장
  • 업계 일반 룰
👎 단점
  • D-N 기준 합의 필요
  • 구현 복잡도 ↑
옵션 E

마진 조건부 Lock

첫 충족 → 출발확정 → 취소로 마진(예: -2명)까지 유지 / 그 이상 미달 시 해제
margin = 2 // 합의 필요
if booked >= threshold and !locked:
  status = 출발확정; locked = True
if locked and booked < threshold - margin:
  status = 예약완료; locked = False
👍 장점
  • 유연 + 안정 균형
  • 소규모 변동 흡수
👎 단점
  • 마진 기준 결정 필요
  • 운영자가 마진 이해해야
  • 여전히 토글 가능
