SECTION 01

인증 & 호출 방식

V2 API Secret + Authorization 헤더 + 쿼리 파라미터로 JSON 전달

1인증 헤더
포트원 콘솔(연동 관리 → 식별코드·API Keys → V2 API)에서 발급받은 Secret을 Authorization 헤더에 담아 호출합니다.
Authorization: PortOne {API_SECRET}
💡 V1 사용자도 V2 Secret 발급 필요
포트원 V1 결제를 사용 중이더라도 거래대사 API는 V2 전용이므로 V2 API Secret을 별도 발급해야 합니다.
2API Server Host
https://api.portone.io
3파라미터 전달 방식 — GET + URL 인코딩된 JSON
포트원 GET API는 쿼리 파라미터로 JSON Body를 받습니다. JSON 생성 → URL 인코딩 → 지정 쿼리 파라미터에 담기의 순서로 호출합니다.
① 전달할 JSON
{
  "name": "홍길동",
  "transactionAmount": 10000,
  "transactionDate": "2024-01-01",
  "isDeleted": false
}
② URL 인코딩 → API 호출
https://api.portone.io/example?parameter=%7B%0A%20%20%22name%22%3A%20%22%ED%99%8D%EA%B8%B8%EB%8F%99%22...
4에러 응답
상태 코드의미
200 OK정상 처리
400 Bad Request요청 입력값 유효성 실패

SECTION 02 · API #1

거래대사 & 정산 내역 조회 API

건별 상세 거래대사 정보 — 가장 핵심 API. 우리 시스템 적재의 1차 소스

GEThttps://api.portone.io/payment-reconciliations?requestBody={URL인코딩된JSON}
REQrequestBody 스키마
필드타입필수설명
dateCondition ReconciliationDateConditionInput 필수 조회 날짜 범위. 최대 3개월. 하위 필드는 transactionDateRange 또는 settlementDateRange 중 하나 (둘 함께 사용 불가)
size Int 필수 한 번에 조회할 개수. 최대 1000
after String 선택 이전 페이지 마지막 커서 (페이지네이션)
요청 예시
{
  "dateCondition": {
    "transactionDateRange": {
      "from": "2024-06-01",
      "until": "2024-06-04"
    }
  },
  "size": 1000,
  "after": "MDE4ZWQwNWItNGRlOS03OGFiLTljYTYtZmU3NDI4MjI5OWUyIyMj"
}
RES응답 구조 (Response Body)
필드타입설명
itemsArray<PaymentReconciliationWithCursor>조회 결과 리스트 (각 item + cursor)
items[].itemPaymentReconciliation (oneOf 4종)개별 거래대사 건 — status 값에 따라 스키마가 분기됨
items[].cursorString해당 item을 가리키는 커서 (페이지네이션용)
pageInfoPageInfostartCursor / endCursor / hasPreviousPage / hasNextPage
⏰ 조회 시점 제약
PG사 거래/정산 내역을 포트원 DB에 저장하기까지 시간이 걸리므로, 전일자 데이터는 익일 12:00 이후부터 조회 권장. 그 이전에 호출하면 누락된 데이터를 받을 수 있음.
SECTION 03

PaymentReconciliation — 응답 oneOf 4종

status 필드 값에 따라 스키마가 달라짐. 4개 중 하나의 타입을 가짐

a. MATCHED
정상
PG ↔ 포트원 일치
b. NOT_MATCHED
불일치
+ anomalyAmount, notMatchedReasons
c. INCOMPARABLE
대사 불능
PG만 있음, 포트원 없음
d. NOT_COLLECTED
미수집
정산만 있음, 거래 미수집
a. PaymentReconciliationMatched — status: "MATCHED"
공통 필드: id / transactionId(포트원 결제ID) / paymentId(고객사 결제ID) / merchantId / storeId / pgTxId / pgSpecifier / actionType / paymentMethod / paymentCurrency / paymentAmount / taxFreeAmount / vatAmount / supplyAmount / paidAt / portonePaidAt(2025-06-26 수집건부터 필수) / orderName / isEscrow / settlement
b. PaymentReconciliationNotMatched — status: "NOT_MATCHED"
MATCHED + 추가 필드:
  • anomalyAmount (Int64, 필수) — PG 기준 거래금액 − 포트원 기준 거래금액 차액
  • notMatchedReasons (Array<NotMatchedReason>, 필수) — 불일치 사유 6종 중 다중 가능
c. PaymentReconciliationIncomparable — status: "INCOMPARABLE"
MATCHED와 차이:
  • transactionId, paymentId, storeId, orderName, supplyAmount — 포트원에 없는 거래라서 누락 (필수 아님)
  • anomalyAmount (필수) — 거래금액 절대값
d. PaymentReconciliationNotCollected — status: "NOT_COLLECTED"
포트원의 PG 정산 서비스는 PG 거래 내역을 먼저 가져와 거래 대사를 진행한 뒤, 정산일에 정산 정보가 채워지는 방식. 이용 초기에 PG 정산내역에 존재하는 거래의 거래일이 서비스 이용 시작일보다 빠르면 이 케이스 발생.

INCOMPARABLE과 차이:
  • pgTxId — 선택 (UPLUS는 제공 불가)
  • portonePaidAt — 선택
📦Settlement (정산 정보 — 모든 타입 공통, 선택 필드)
필드타입설명
feeAmountInt64정산 수수료
feeVatAmountInt64정산 수수료 부가세
settlementAmountInt64실제 정산 금액
settlementCurrencyString정산 통화 (ISO 4217)
settlementDateString정산 일자
freeInterestFeeInt64 (선택)상점부담무이자 수수료 — KCP 카드 거래에서만 제공
💱 ISO 4217 마이너 단위 처리
모든 금액은 통화 마이너 단위만큼 소수점을 우측으로 옮겨 정수로 반환. 예: 4.10 USD → 410 (USD 마이너 단위 = 2). KRW는 마이너 단위 0이라 그대로.
SECTION 04

ReconciliationPaymentMethod — 결제수단 9종 (oneOf)

type 필드 값에 따라 추가 필드가 달라짐

type 추가 필드 비고 / 트립스토어 사용
CARD issuer (CardCompany) / acquirer (CardCompany) / approvalNumber / installmentMonth (Int) 신용카드 결제 — 메인 결제수단
VIRTUAL_ACCOUNT bank (Bank) / approvalNumber 가상계좌
TRANSFER bank (Bank) / approvalNumber 계좌이체
EASY_PAY provider (ReconciliationEasyPayProvider) / method (PaymentMethod 재귀) 간편결제 — provider로 구분 (KAKAOPAY/NAVERPAY/TOSSPAY 등) + method.type으로 내부 실제 결제수단 (CARD 등) 표현
CHARGE — 간편결제 포인트 충전
GIFT_CERTIFICATE approvalNumber / giftCertificateType (5종) 상품권 (스마트문상/문상/도서문상/컬쳐랜드/해피머니)
MOBILE carrier (Enum 6종) 휴대폰 결제 — 트립스토어 미운영
ARS — ARS 결제
ETC name (String, 필수) 기타 결제수단
🔁 EASY_PAY의 재귀 구조
EASY_PAY의 method 필드는 다시 PaymentMethod 타입을 가짐. 예: 카카오페이로 카드 결제 시 → type: EASY_PAY, provider: KAKAOPAY, method.type: CARD, method.issuer: KOOKMIN_CARD.

SECTION 08

구현 체크리스트

API 클라이언트 구현 시 빠뜨리지 말아야 할 항목들

✅HTTP 클라이언트 레벨
  • 인증 헤더 포맷: Authorization: PortOne {API_SECRET} (Bearer 아님 주의)
  • GET 방식 + 쿼리 파라미터에 URL 인코딩된 JSON — POST 아님
  • 에러 응답 401/403 시 Secret 만료/권한 점검 알림 발송
  • 스케줄러 트리거: 전일자 → 익일 12:00 이후 (안전 마진 두고 13:00)
✅페이지네이션
  • 1회 최대 size: 1000 + after 커서
  • 최대 조회 범위 3개월 초과 시 자동 분할
  • pageInfo.hasNextPage = true인 동안 endCursor로 반복 호출
✅oneOf 응답 파싱
  • status 필드로 4종 타입 분기 (MATCHED / NOT_MATCHED / INCOMPARABLE / NOT_COLLECTED)
  • INCOMPARABLE/NOT_COLLECTED는 transactionId, paymentId, storeId 등 누락 가능 → nullable 처리
  • paymentMethod.type으로 9종 결제수단 분기 (CARD/EASY_PAY/VIRTUAL_ACCOUNT 등)
  • EASY_PAY의 method 필드는 PaymentMethod 재귀 — 파서 재귀 호출 필요
✅금액 처리
  • 모든 금액은 Int64. ISO 4217 마이너 단위만큼 소수점 우측 이동된 정수
  • KRW는 마이너 단위 0이므로 그대로 / USD는 2이므로 410 = 4.10 USD
  • anomalyAmount는 status에 따라 의미 다름 (차액 vs 절대값) — 다음 슬라이드 참조
✅Enum 매핑 테이블
  • actionType 5종 + NotMatchedReason 6종 → 우리 컬럼 enum으로 변환
  • CardCompany 65+종 / Bank 60+종 → financial_institution 컬럼에 그대로 또는 한글명 매핑
  • pgProvider 21종 / EasyPayProvider 19종 → 결제수단 표시명 매핑 테이블 사전 구축
  • 신규 enum 추가 시 대응: 알 수 없는 값은 raw 그대로 저장 + 알림
