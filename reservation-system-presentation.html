BACKGROUND

지금 예약시스템의 한계

"하나의 예약 = 일관된 금액 흐름"이 안 되는 구조적 문제

🔴 운영상의 한계

  • 예약 1건에 결제주체가 둘 → 예약을 2건으로 쪼개서 운영
  • 예약·결제 금액 이력이 덮어쓰기로 사라짐
  • 운영자 수기 관리·엑셀 의존도 ↑
  • 금액 변경/조정 과정 오류 위험

📉 비즈니스 임팩트

  • 여행사 결제분 → 플랫폼 수수료 누락 (수익 손실)
  • 결제 ≠ 정산 케이스 추적 불가
  • 취소율 데이터 왜곡 (행사변경 = 가짜 취소)
  • "우리 예약 1건의 순이익"을 시스템으로 계산 불가
📒 신규 시스템 핵심 컨셉: 예약 1건마다 "가계부(원장)"를 두고 모든 금액 흐름을 한 줄씩 기록 → 결제·환불·정산·금액수정 이력을 끊김 없이 추적

1차 ① · 진행중

원장 개념 추가

모든 후속 과제의 기반. 예약 = 가계부 1권 구조 정착

📈 효용

  • 4주체(고객·채널·플랫폼·여행사) 잔액을 시스템으로 검증
  • "결제 금액 ≠ 정산 금액" 케이스 이력 기반 설명
  • 예약 1건의 순이익 자동 계산 가능
  • 모든 후속 과제(②~⑨)가 이 위에서 동작

📦 산출물

  • BE: 7개 API (원장 조회/잔액/금액 가감/취소정보)
  • FE: 기본탭 + 원장탭 (4 서브탭)
  • 주체별 잔액 카드 (4개)

🛠 진행 방안

  1. DB 스키마 안착 완료
  2. BE API 7종 구현 P0
  3. FE 어드민 화면 (원장탭 + 주체별 잔액)
  4. +금액/−금액 모달 (금액 직접수정 금지)
  5. 운영팀 트레이닝 + 정책문서 SSOT 배포
🔑 핵심 제약: 금액 직접 수정 불가. 모든 변동은 +추가/−차감으로 원장 행 추가
